# OmniMatch and Pattern Matching in SymPy

- Francesco forked MatchPy into OmniMatch: associative, commutative, one-identity pattern matching
  - Uses a generalized discrimination network: blends thousands of rules into a single indexed structure
  - Matches all rules in one tree traversal, vs. SymPy’s current for-loop approach
  - Tested on Ruby integration project with 6,000-7,000 Mathematica rules: loads in ~30s, matches in milliseconds; ~1 GB memory
- SymPy Matching: separate bridge package to convert SymPy expressions to/from OmniMatch
- Constraints supported: free-of constraints, custom lambda predicates (used heavily in Ruby rules)
- Current limitation: matches from root only, no built-in subtree search
  - Workaround: iterate subexpressions and feed one by one
  - True subtree matching would be a research project
- Aaron suggested trying OmniMatch in SymPy; Francesco noted it would require adding a dependency
  - Best candidate areas: Refine (with identity-based rules), matrix expressions module, solvers, tensor module
  - Most SymPy algorithms are tree traversals and could be rewritten with pattern matching

# SymPy Core Performance and Proto-SymPy

- Core bottleneck: object constructors do automatic simplification transforms (e.g., Add can return Mul)
  - Not portable to C++ or Rust; breaks type safety assumptions
  - Changing core risks breaking downstream libraries
- Matrix expression module written without this pattern: type-safe, but less automatic
- Oscar’s proto-SymPy idea: a separate fast core with automatic simplification disabled
  - Used internally for pattern matching object construction, invisible to end users
  - Oscar also building a Rust version
- MatchPy load time (~30s for Ruby rules): ~15s attributable to SymPy class constructors, not the matching library itself
